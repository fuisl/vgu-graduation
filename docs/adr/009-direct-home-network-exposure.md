# ADR-009: Direct home network exposure, no Cloudflare Tunnel
Status: Accepted
Date: 2026-09-27
## Context
ADR-001 and section 8 of the target architecture put Cloudflare (Free plan) in front of the homelab: the zone's nameservers on Cloudflare, a Cloudflare Tunnel (`cloudflared`) so the router never opens an inbound port, Cloudflare terminating TLS, and its WAF/rate-limiting protecting token lookups. The homelab router can in fact do manual port forwarding, and the decision is to use that instead.
## Decision
The router forwards ports 80 and 443 directly to the k3s node's Traefik. There is no Cloudflare Tunnel, no Cloudflare proxy, and no Cloudflare WAF, cache rule, or Access application. DNS stays at Spaceship, unchanged from today; the zone's nameservers do not move to Cloudflare. `api.grad26.fuisloy.dev` (and any future public hostname on this node) is a plain `A` record pointed at the home connection's current public IP, kept current by a Dynamic DNS updater running in the cluster, since the connection's IP is dynamic (this also covers the documented 4G/5G failover WAN). Traefik terminates TLS itself, using a `cert-manager` `ClusterIssuer` with the **HTTP-01** challenge (not DNS-01: DNS is not on Cloudflare, so there is no DNS API to automate against, and HTTP-01 needs nothing from the registrar beyond the `A` record already required). Traefik's own rate-limiting middleware (already planned) is the only rate-limiting layer; there is no edge WAF or DDoS scrubbing in front of it.
## Alternatives considered
- Cloudflare Tunnel (the previous decision, ADR-001/section 8.2): no inbound port ever needed, WAF and DDoS protection, TLS terminated at Cloudflare's edge, one rate-limit rule on the Free plan. Superseded by this ADR.
- Cloudflare proxied `A` record without the Tunnel product specifically (still port-forwarded, but Cloudflare's edge still proxies traffic and provides WAF/cache): keeps most of the Tunnel's protection while still port-forwarding. Considered and declined in favor of no Cloudflare involvement at all.
- DNS-01 via a Cloudflare API token while keeping DNS itself at Spaceship: not possible — DNS-01 requires the challenge provider to be able to edit the zone's actual DNS records, which needs the zone hosted there.
## Consequences
- The home connection's real public IP is directly visible to anyone who resolves `api.grad26.fuisloy.dev` or scans for it. There is no edge shielding it, unlike the Tunnel model.
- No WAF, no DDoS protection, no Cloudflare cache rule. Section 10 (security summary) and section 9 (homelab robustness) are updated to state this as an accepted residual risk rather than implying Cloudflare mitigates it.
- A Dynamic DNS updater becomes a new, small dependency: if it fails silently after the IP changes, `api.grad26.fuisloy.dev` silently stops resolving to the right place. It needs the same kind of monitoring as everything else in section 9's risk table. Spaceship has a real DNS API (`docs.spaceship.dev`, `PUT /v1/dns/records/{domain}`, key/secret auth) that this can call directly.
- The router must forward only ports 80/443 to Traefik — never to Postgres, Garage, the GPU service, or the printer, which keeps the "never expose these directly" rule in `AGENTS.md` intact. Port forwarding widens the *edge*, not what sits behind it.
- HTTP-01 cannot issue a wildcard certificate. The deferred `venue.grad26.fuisloy.dev` open item (section 8.7) will need its own certificate request when it's taken up, same as today, just via HTTP-01 instead of DNS-01.
- Removes `cloudflared`, its Deployment, its Secret, the `edge` namespace's reason for existing (only the static fallback remains there), and the Cloudflare API token Secret entirely from the infrastructure repository.
## Implementation (2026-09-27)
Reinstated after a same-day revert to the Tunnel model. The deciding points: the Dynamic DNS updater the revert wanted to avoid is small and is now built and tested; Cloudflare's free Universal SSL covers only one level of subdomain, so `api.grad26.fuisloy.dev` would need Advanced Certificate Manager (paid) or a hostname change that breaks the `.grad26.fuisloy.dev` cookie scope (ADR-003); and moving the nameservers would also mean removing the zone's DNSSEC DS record first. Live in the infrastructure repository:
- Router: TCP 80/443 forwarded to the node on the PPPoE WAN (public IPv4, no CGNAT); router admin not exposed on the WAN; inbound IPv6 dropped.
- DNS at Spaceship: `A api.grad26` (TTL 300) kept current by the `ddns` CronJob; `grad26` CNAME to Vercel; the apex and `www` redirect to `grad26.fuisloy.dev` in Vercel.
- cert-manager v1.21.2 with `letsencrypt-staging` and `letsencrypt-prod` ClusterIssuers (HTTP-01 via Traefik); the production certificate is issued.
- Traefik: HTTP to HTTPS redirect, HSTS and security headers, `Cache-Control: no-store` on API responses, a per-client-IP rate limit (`externalTrafficPolicy: Local` so Traefik sees real client IPs), JSON access logs without request paths or headers, and `/admin/*` refused with 403 until admin authentication exists.
