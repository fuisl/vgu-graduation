# ADR-010: Site languages without locale URLs
Status: Accepted
Date: 2026-10-19
## Context
The site UI and event information support English and Vietnamese, with English as the fallback (#9, `architecture/target/open-items-and-decisions.md`). German is a live-caption language only. Most guests are families on phones at the venue, and invitation URLs are bearer credentials (`/invite/<token>`) that are already sent out and must not change. Before this decision every string was English and hard-coded, the landing, venue, invitation, profile and guide pages were rendered per request, and `/memories`, `/gallery`, `/wishes`, `/about` and a few others were static or ISR pages on Vercel.
## Decision
- **No locale in the URL.** The language is a `lang` cookie (`en` or `vi`, one year, `SameSite=Lax`, `HttpOnly`, `Secure` in production), else the browser's `Accept-Language` (the first `vi*` or `en*` tag by quality), else English. `lib/i18n/server.ts` resolves it once per request (`getLocale`, `getI18n`); the root layout writes `<html lang>`. Admin is internal and stays English (`lang="en"` on its root).
- **Switching** is a plain form: an EN | VI mono pill in the header action slot, the mobile menu sheet and the footer posts to `POST /api/locale`, which sets the cookie and answers `303` to the path the guest was on. The path comes from a hidden field rendered by `usePathname` on the server, so it works without JavaScript; `safeReturnPath` keeps only a same-site path (no query string, no fragment) and collapses `/invite/<anything>` to `/invite`, so a token can never be echoed.
- **Dictionaries are TypeScript objects** keyed by dotted message ids: `lib/i18n/messages/en.ts` is the source of truth and `vi.ts` is typed `Messages`, so a missing or extra key fails `tsc`, and a test compares the key sets and placeholders. At runtime a missing translation falls back to English with a development warning. Plurals are `.one` / `.other` pairs; placeholders are `{name}`; `formatRich` places links inside a sentence. No i18n library.
- **Server components get a translator; client components get a slice.** Pages call `getI18n()` and pass `i18n` to the shared shell and server components; client components receive `pickMessages(locale, "prefix.")` as a prop and format it with `sliceTranslator`. Neither dictionary is bundled for the browser.
- **Rendering per request instead of per-locale static pages.** Reading the cookie in the root layout makes every page dynamic. The API data those pages show stays in the Next fetch cache with the same `revalidate` seconds and cache tags (`event`, `gallery-public`, `wishes-public`, invitation tags), so admin revalidation still reaches them and the API sees no extra load; only the HTML is rendered per request. Nothing cached can carry the other language: page HTML is no longer cached, and the one public CDN-cached BFF response with copy in it (`/api/gallery`) now sends language-neutral fields (`sender: null`, `audience`) that the client labels.
- **Event information:** proper nouns (venue name, programme and building names) stay as they are. The prose fields get optional Vietnamese twins, `nameVi`, `venue.addressVi` and `arrivalInfoVi` (contract, migration `0006_event_vietnamese`, admin event form); `localizeEvent` uses them for Vietnamese readers and falls back to English. The subscribable `.ics` feed is one shared file and stays English; the Google and Outlook links are built in the guest's language.
- **Dates** use `Intl` with `en-GB` (as before) or `vi-VN`; the landing hero keeps `en-US` ("November 20") in English.
## Alternatives considered
- A `[locale]` route segment behind a middleware rewrite (next-intl's `localePrefix: "never"` pattern): keeps static and ISR pages per locale, but moves every route under `app/[locale]`, needs a second root layout for admin and a catch-all for not-found, and runs middleware on every request. Rejected for now: the pages that guests open most (landing, invitation, venue, profile, guide) were already dynamic, and the data cache keeps the API load the same. Revisit if the archive pages become hot after the event.
- Locale-prefixed URLs (`/vi/venue`): would change shared links and invitation URLs. Rejected.
- Rendering both languages and swapping with CSS: doubles HTML on slow venue networks. Rejected.
- next-intl or another i18n library: more client JavaScript and configuration than two languages need.
## Consequences
- Every guest page is server-rendered per request (Vercel functions); `/memories`, `/memories/timeline`, `/gallery`, `/wishes`, `/polaroid`, `/live`, `/about` and the experimental pages lost static or ISR page caching. First-load JavaScript is unchanged (shared 103 kB; per-page changes within about 1 kB).
- New copy must go through the dictionaries (`design/llm-reference.md`, "Copy and languages"). The Vietnamese file is a draft for native-speaker review (`TODO(owner)` at its top).
- Content typed by admins and guests (guide-book items, wishes, names) is shown as written, in one language.
- Live captions keep their own language choice (de, en, vi); a guest reading the site in Vietnamese starts on Vietnamese captions.
