# ADR-012: Guest email through the owner's Gmail over SMTP
Status: Accepted
Date: 2026-10-19
## Context
Until now no email went to guests (decided 2026-09-29, `architecture/target/open-items-and-decisions.md`). Admins copied each invitation link from the admin page and sent it themselves, and the venue page's "Get the calendar invite by email" form was hidden because nothing could send it (QA P1-3). The owner decided on 2026-10-19 to send three emails: the invitation link, the calendar invite a guest asks for, and an RSVP confirmation. They should come from the owner's own Gmail address, so guests see a sender they know. There are a few hundred guests and no other mail infrastructure.
## Decision
- **Gmail SMTP submission with an app password.** The API and worker log in to `smtp.gmail.com:587` with STARTTLS required (nodemailer), as `SMTP_USER` with a Google app password in `SMTP_PASSWORD`. Both live in a SOPS-encrypted Secret `api-mail` mounted into the API and worker. `MAIL_FROM` sets the display name. Mail is on only when both credentials are set; without them every email reports `not_configured`, `GET /mail/status` says `enabled: false` and the venue form stays hidden. Host and port are configurable, so a transactional provider can replace Gmail without code changes.
- **The invitation link is sent inline, at issue or rotate time.** Only the token's hash is stored, so the link exists only in the response to `POST /admin/invitations` or `POST /admin/invitations/{id}/rotate`. With `sendEmail: true` the API mails it to the guest's stored address before answering, and returns `emailStatus` (`sent`, `failed`, `no_address`, `not_configured`) next to the link. The link is still shown once in the admin UI, so a failed email loses nothing. A slow server fails the email after 15 seconds instead of hanging the admin.
- **The calendar invite is sent inline from `POST /calendar/email`.** It needs an invitation credential (the venue page shows the form only to guests with the `inv` cookie, and only while mail is on). Each invitation may send `CALENDAR_EMAIL_LIMIT` (5) per day, counted in memory per API process, so the endpoint cannot be used to mail strangers. The email carries the `.ics` as an attachment and the `webcal://` feed link, since only the feed updates when the time is confirmed. The address the guest types is used for that one send and never stored.
- **The RSVP confirmation is a worker job.** `PUT /rsvp` queues `mail.rsvp_confirmation` two minutes ahead when mail is on and the guest has a stored address. The payload is the invitation id and the RSVP's `updatedAt`, never an address. When it runs, the worker reads the current answer and skips if a newer save exists, the invitation was revoked or the address was removed, so a guest who edits three times gets one email. SMTP failures retry with the queue's backoff. The email states attendance and plus-ones only: accessibility needs, dietary requirements and notes stay out of mailboxes.
- **Plain text, Vietnamese then English.** We don't know which language a guest reads, so the invitation and RSVP emails carry both. The calendar invite is asked for from the site and uses the site's language. No HTML, images or tracking pixels.
- **Privacy.** Addresses and links are never logged: mail code logs invitation ids and the email status, `email` is in the log redaction list, nodemailer's logger is off, and a failed job stores only nodemailer's error code (an SMTP reply can quote the address).
## Alternatives considered
- A transactional provider (Resend, Postmark, SES) on a `fuisloy.dev` address: better deliverability and higher limits, but it needs SPF and DKIM records and a new account, and guests would not see a familiar sender. The SMTP settings are generic, so this stays a configuration change if Gmail falls short.
- The Gmail API with OAuth: no stored password, but it needs a Google Cloud project, a consent screen and refresh-token handling for one mailbox. An app password is revocable on its own and simpler to rotate.
- Queueing every email: the invitation link can't be queued without storing the raw token, which the data model forbids, and the calendar invite would mean storing a typed address. Both send inline instead.
- Admins keep sending links by hand: still possible (the link is always shown), but slow for a few hundred guests.
## Consequences
- Every email is copied to the Sent folder of the owner's Gmail, including invitation links. That mailbox now holds bearer credentials and guest addresses: protect it with 2-step verification, don't share it, and clear the Sent folder after the event if you want it gone.
- Gmail limits a personal account to about 500 recipients a day. Issue invitations in batches if the guest list is bigger. Over the limit, Gmail refuses sends for up to a day; the admin sees `failed` and copies links by hand meanwhile.
- Mail from a personal address sent by a server can land in spam. The admin notice says so, and the venue form keeps the `.ics` download as the fallback.
- The API and worker need egress to the internet on port 587 (`allow-mail-egress` in the infrastructure repository); everything else stays default-deny.
- Revoking the app password in the Google account stops all email at once; the site keeps working and the forms report `failed` until the Secret is updated.

**Update 2026-10-30 (owner):** the invitation and RSVP emails, and every bilingual email after them, now carry English first, then Vietnamese, with the subject, preheader and heading in English.
